# Week 01 — Product Analytics & KPI Foundations

**Roadmap:** Digital + AI Product Management (16 Weeks)

**Estimated effort:** 6–8 hours  
**Status:** Not Started

Learn how Product Managers use data to understand customer behaviour, measure product performance, identify opportunities and make product decisions.

The goal is to develop transferable Product Management skills, **not to become an Amplitude expert**.

**Estimated time:** 60 minutes

## Goal

Understand how users move through a product and how PMs identify friction in customer journeys.

## What to Learn

- Conversion funnels.
- Funnel stages and user events.
- Step-to-step conversion.
- Overall conversion.
- Drop-off rates.
- Conversion windows.
- Why correlation does not establish causation.

## Learning Resources

### Resource 1 — Amplitude: Understanding User Behavior

https://amplitude.com/understanding-user-behavior

**Read:** Step Three — Optimize Conversion Funnels.

### Resource 2 — Amplitude Analytics Documentation

https://amplitude.com/docs/analytics

**Find and study:** Funnel Analysis.

## Practical Exercise

Analyse this hypothetical K-beauty funnel:

| Funnel Stage | Users |
|---|---:|
| Open app | 1,000 |
| View product | 650 |
| Add to cart | 200 |
| Complete purchase | 80 |

Assume these are unique users progressing through the ordered funnel within a seven-day conversion window.

Calculate:

1. App open → Product view conversion.
2. Product view → Add to cart conversion.
3. Add to cart → Purchase conversion.
4. Overall app open → Purchase conversion.

Then answer:

- Where is the largest percentage drop-off?
- Which transition would you investigate first, and why?
- What are three possible explanations?
- What additional evidence would you collect?
- What product improvement might you test?

**Save to:** `conversion-funnel.md`

# Day 5 — Events, Properties & Event Dictionaries

**Estimated time:** 60–75 minutes

## Goal

Understand how user actions become analytics events and how to define a tracking plan.

## What to Learn

- Events and event triggers.
- Event properties.
- User properties.
- Event naming conventions.
- Event dictionaries.
- Tracking plans.
- How events support KPI calculations.
- Data quality and duplicate events.

## Learning Resources

### Resource 1 — Amplitude: Product Analytics Fundamentals

https://amplitude.com/product-analytics-fundamentals

**Study:**
- Step One — Laying the Data Foundation.
- Step Two — Create & Manage Custom Events.
- Step Three — Understand Event & User Properties.

**Prioritise these named materials:**
- Custom Events Overview.
- Event and User Properties.
- User Property Definitions.
- Event Property Definitions.

### Resource 2 — Amplitude: Product Analytics Guide

https://amplitude.com/explore/analytics/product-analytics-guide

**Revisit:**
- Define your critical events.
- Create a tracking plan.

## Practical Exercise

Create Deliverable 2: **Event Dictionary**.

Start with these events:

| Event | Trigger |
|---|---|
| `app_opened` | User opens the application |
| `product_viewed` | User views product details |
| `product_saved` | User saves a product |
| `add_to_cart` | User adds a product to their cart |
| `purchase_completed` | Successful purchase confirmed |

For every event, document:

- Event name.
- Event description.
- Exact trigger.
- Required properties.
- Property data types.
- Related KPI.
- Edge cases or exclusions.
- Duplicate-event prevention, where relevant.

Consider whether you need additional events to calculate every KPI in your metric tree.

**Save to:** `event-dictionary.md`

## Learning Resources

**Focus on:** How engagement and retention metrics are defined.

### Resource 3 — Amplitude: Understanding User Behavior

https://amplitude.com/understanding-user-behavior

**Revisit:** Funnel analysis and retention measurement.

**Note:** The baseline-assumption exercise below is an additional practical PM exercise, not a specific Amplitude course.

## Practical Exercise

Create Deliverable 3: **Baseline Assumptions**.

Use the following illustrative values as a starting exercise:

| KPI | Hypothetical Baseline | Proposed Target |
|---|---:|---:|
| Monthly active users | 10,000 | 12,000 |
| Product save rate | 15% | 20% |
| First-purchase conversion rate | 3% | 4% |
| 30-day repeat purchase rate | 18% | 24% |
| Monthly repeat purchasing customers | 600 | 850 |

These figures are invented for learning purposes. They are not actual company data or validated industry benchmarks.

For every KPI, answer:

1. Why did I choose this baseline?
2. Is it observed, estimated or hypothetical?
3. What population and time window does it describe?
4. What data would validate it?
5. Why might the proposed target be achievable?
6. What could make my assumption incorrect?

Check that your metrics use compatible definitions and that any relationships between them are mathematically consistent.

**Save to:** `baseline-assumptions.md`
